# Codex instructions for this repo

## 0) What you are (Codex) expected to do
You are an implementation agent working inside this repository.

**Before changing anything**
1. Read the relevant files and summarize what exists (paths + key functions).
2. Propose **2–3 options** (tradeoffs, risks, migration cost).
3. Ask the user to choose an option **only when truly necessary**; otherwise pick the safest option and proceed.

**When you change code**
- Prefer **TDD**: add/adjust tests first, then implement.
- Make **small, reviewable diffs**.
- Run the closest automated checks (unit tests first, then integration).
- Update docs/config when behavior changes.

---

## 1) Project purpose
Build a **local-first**, AWS-compatible pipeline to monitor Calgary real-estate listings:
- daily scrape (source strategy-based; currently includes `zolo.ca`)
- idempotent ingestion
- property identity / dedup logic (stable identity across re-scrapes)
- history tracking (changes over time)
- easy migration to low-cost AWS later (S3/SQS/RDS equivalents)

Primary outputs:
- **raw** captured pages/data
- **normalized** entities in Postgres
- **errors** stored and queryable (no silent drops)

---

## 2) Non-goals (for now)
- No UI-heavy features in this repo (API is read-only; client app can live elsewhere).
- No managed/cloud-only dependencies in dev.
- No premature performance optimizations that reduce correctness/idempotency.

---

## 3) Hard constraints (do not violate)
- **ARM64 containers only**
- Local dev uses: **Docker + LocalStack + Postgres**
- **Idempotency > performance**
- Preserve **raw + normalized + error** data
- Do not introduce services that can’t be emulated locally (LocalStack-compatible only)

---

## 4) Architecture (current shape + direction)
This repo is a **monorepo (split-ready later)** with:
- `infra/`: Docker compose + LocalStack + Postgres, networks, ports
- `services/`:
  - `scraper/`: fetches listing pages, emits work, stores raw
  - `parser/`: consumes work, normalizes, upserts into Postgres, records errors
  - `api/`: read-only query API over Postgres (no mutation)
- `scripts/`: bootstrap + test helpers (some scripts enforce safety rails)

Event-driven intent:
- Scraper produces messages (SQS) and stores raw payloads (S3).
- Parser consumes messages, reads raw payloads, writes normalized records (Postgres).
- Errors are stored (Postgres and/or raw bucket) with enough context to debug.

---

## 5) Environment & stacks
We run multiple “stacks” (at least `test` and `run`).

**Safety rails**
- Integration scripts must refuse to run against “run/default” ports by accident.
- If a script checks `STACK=test` and refuses ports like `4566` / `5432`, keep that behavior.

**Config principles**
- All services must be configurable via env vars (12-factor style).
- Validate required env vars early and fail fast with clear errors.

Common examples used in this repo (non-exhaustive):
- `SCRAPER_STRATEGY` (e.g., `zolo_ca`)
- `ZOLO_ENTRYPOINT_URL`
- `RAW_BUCKET` (S3 bucket in LocalStack)
- LocalStack endpoint/ports (typically `4566` but stack-dependent)
- Postgres port (typically `5432` but stack-dependent)
- `DRY_RUN` is supported in some flows; when enabled, it must not emit messages nor write state.

---

## 6) Data & identity rules (idempotency and dedup)
**Idempotency is a hard requirement**:
- Re-running the same inputs must not create duplicates.
- Upserts should be deterministic and keyed by a stable identity.

**Three persistence lanes**
1. **Raw lane**: store fetched pages / payloads (S3-compatible)
2. **Normalized lane**: canonical domain tables in Postgres
3. **Error lane**: store parsing/validation issues with enough context to replay/debug

**Property / listing identity**
- Identity must be **stable across time** and resilient to URL changes when possible.
- If multiple candidate keys exist (URL id, address+unit, external ids), implement a clear precedence rule and document it in code + tests.
- When identity logic changes, add a migration strategy (even if “rebuild from raw”).

> Important: do not “invent” identity fields. Derive identity from fields that already exist in the scraped/normalized model, and back it with tests.

---

## 7) Scraper rules (correctness > cleverness)
- Treat each source as a strategy module (no source-specific hacks leaking everywhere).
- Respect rate limiting and avoid aggressive concurrency by default.
- Every fetched page should either:
  - be written to the raw lane and queued for parsing, or
  - be recorded as an error with context (HTTP status, URL, timestamp, retryability)

---

## 8) Parser rules (deterministic normalization)
- Parser must be deterministic: same raw input => same normalized output.
- Validation errors must be captured (not just logged).
- Normalize with explicit mappings (no “best effort” silent coercion that hides problems).
- Upserts must be atomic where possible; prefer transactions for multi-table writes.

---

## 9) Testing strategy (test pyramid)
Default posture: **max unit tests, necessary integration tests, minimal E2E**.

### Unit tests
- Domain logic (identity, parsing/normalization, mapping) should be unit-tested heavily.
- Avoid network calls.

### Integration tests
- Use Docker + LocalStack + Postgres in a `test` stack.
- Scripts may enforce ports/stack checks; keep those guardrails.

### E2E (minimal)
- Only for the most critical “happy path”:
  scrape -> raw -> queue -> parse -> db rows.

**Definition of Done for changes**
- Tests added/updated for the changed behavior
- All relevant tests pass locally
- No regression in idempotency
- Raw/normalized/error lanes still preserved

---

## 10) Code style & craftsmanship
- Prefer clear boundaries (DDD-ish): domain logic isolated from infra adapters.
- Keep dependencies explicit (interfaces at boundaries).
- Logging should be structured and useful for debugging pipeline runs.
- Avoid big refactors mixed with behavior changes; do one thing per PR.

---

## 11) Operational hygiene
- Always provide a short “how to verify” section with commands after changes.
- Prefer scripts in `scripts/` for repeatable checks.
- If you add a new env var, document it and validate it at startup.

---

## 12) When uncertain
- Prefer correctness and traceability over speed.
- If tradeoffs are non-obvious, present options and pick the safest default.
- Never remove safety rails that prevent accidental writes to the wrong stack.
